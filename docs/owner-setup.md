# Owner setup wizard

Run the installed tg-mcp-owner setup as the original ordinary OS user. The launcher requests scoped elevation for the protected coordinator; do not run the launcher with sudo. Windows uses C:\ProgramData\TelegramMCPGateway\bin\tg-mcp-owner.cmd setup.

The combined installation command returns from its scoped system installation and offers Configure now or Configure later in the same ordinary terminal. The separate installed setup command remains available for retries.

The wizard uses account `personal` and permission profile `owner` without ordinary label questions. An existing custom or ambiguous account/profile requires `tg-mcp-owner setup --advanced` with the installed command path, so setup cannot silently create another account or replace a session/token. Advanced labels use 1-32 lowercase letters, digits, "-" or "_", starting with a letter or digit.

Setup recommends console over SSH or on headless Linux, and browser on a local desktop; either choice can be overridden. Arrow keys and Enter select the interface, Space and Enter select multiple clients; limited terminals accept numbered choices or names. Console users choose clients here, browser users after sign-in. Supported IDs are codex, claude, cursor, hermes, opencode and openclaw. A concise warning before secret entry explains that the owner must stop agents/capture and that hidden input cannot prevent same-user capture. No typed readiness phrase is required.

Next the wizard announces the administrator step. On macOS/Linux sudo's own prompt names your computer's administrator password; on Windows, User Account Control asks for approval. Telegram values never go there. Only after elevation, and only when the protected worker requests new credentials or login, does the chosen interface collect Telegram input. A failed first login does not cache an unverified pair. An existing session needing missing credentials is a repair error, not a new-login prompt.

## Browser guide and console entry

Browser mode opens a temporary page on `127.0.0.1` with a random port. Step 1 explains the official `my.telegram.org/apps` flow: sign in, open API development tools, create an application, then paste api_id and api_hash. The field guide is an illustration with example title, short name and platform, not a screenshot of a real account. Users who already have an application use its existing values. Step 2 starts QR login automatically and keeps the phone alternative visible during loading and QR display. QR codes refresh automatically; phone entry proceeds to the Telegram code. Either method requests 2FA when Telegram requires it. Switching QR/phone ends and confirms termination of the old protected conversation before starting another. Already submitted API values remain only in the original user process memory for this wizard and are not durably saved before successful Telegram authorization. The original terminal remains open for service/client checks and final evidence.

Step 3 offers a checklist for Codex, Claude Code, Cursor, Hermes, OpenCode and OpenClaw. Select several or choose Set up later. A conflicting gateway entry needs a separate replacement confirmation. The page receives only client names and safe completion state, never a session or MCP token. Only verified profile/SDK handoff is presented as connected; missing credentials or deferred setup remain incomplete. See [adapter formats and limitations](client-adapters.md).

Press C in the waiting browser terminal to continue in console inside the same wizard. The temporary listener and keyboard reader close, the prior protected worker fully exits and supervision is restored before the next attempt begins. A teardown failure stops setup rather than starting a second owner. The transition retains completed durable state and in-memory API values. Console mode creates no browser page or HTTP listener. The terminal presents a framed YOUR ACTION REQUIRED API guide with the official link and three numbered steps. API ID and phone use ordinary visible input. API hash starts hidden; Ctrl+T shows/hides the editable value, and submitting/cancelling clears its revealed line. OTP and 2FA remain hidden. NO_COLOR disables decorative styling but preserves cursor erasure for safe reveal/editing and multirow cleanup. TERM=dumb and narrow/unknown-width terminals keep the hash hidden and explain the limitation; use a cursor-capable terminal or browser guide to inspect it. Client choices/replacement use the terminal.

Console login offers QR or phone with arrows/Enter and numeric/text fallback. The complete QR has a four-module quiet zone and fixed black-on-white contrast, including functional monochrome ANSI colors in NO_COLOR sessions. It refreshes in place, expires/clears, and is removed before any new human prompt, success or cancellation. The terminal must report enough columns/rows; unsupported or too-small displays stop the current protected attempt before falling back to phone. Login API values remain in owner-process memory for that retry. A separate closed console_qr capability allows private QR frames without enabling browser-only client selection. Console clients remain selected up front. The internal direct administrator/Windows non-broker compatibility paths remain phone-only; use the ordinary installed owner launcher for console QR and the hash reveal control. Browser launch failure also uses this path. Repeating setup reuses saved credentials/session and goes directly to client selection in browser mode.

The browser has no external scripts, images, analytics or browser storage. Its private launch capability is held in the URL fragment, removed from browser history by the page and sent only in an authenticated header. API requests require the exact loopback Host; state-changing requests also require the page's Origin and JSON content type. Requests, values and lifetime are bounded, replayed answers are rejected, and the listener closes after completion or cancellation. Neither credentials nor the capability are included in public progress. As with terminal input, same-user software can inspect this interaction.

The worker sends only closed prompt identifiers, bounded QR-display frames and a client-selection request through its private pipe or protected Windows mailbox. The page sends answers back through that channel; the worker creates and stores the session. QR frames and submitted values are cleared from page state when the next step begins. Repeated submissions cannot discard an accepted form's pending hash/phone value. Browser cancellation ends the private exchange so the coordinator stops the worker before restoring supervision.

## Session ownership and completion

One setup/session lease controls the private worker. The coordinator proves the fixed installed code, service identity and private state before dropping supplementary groups/gid/uid. Every MTProto call goes through the account limiter; session is durably saved before cleanup can terminate a hung login client. Workers/coordinator close their private pipes after their final frame, with bounded exit/cancellation. One-shot authentication workers explicitly exit after client/storage/lease cleanup and final-frame flush, so QR-library refresh timers cannot keep them alive. Prior supervisor registration/recovery/running state is captured in a protected marker and restored after cancellation, crashes or non-activating runs.

The login worker exits and releases its session before daemon startup. Service/listener ownership is proven before credential handoff. The original-user profile adapters write selected client credentials directly; tokens never appear in terminal/logs. A conflicting gateway entry needs explicit REPLACE consent and unrelated settings are preserved. Encrypted pending handoff persists until client configuration, SDK probe and token-hash acknowledgement succeed. The DB-only acknowledgement does not create another MTProto client.

Successful SDK setup makes restarting the actual selected clients the main browser result and a prominent terminal NEXT step. Desktop/CLI instructions describe closing and reopening the tool; Hermes and OpenClaw instructions identify the process/service on the machine hosting the agent. It prints safe evidence and tells the human which clients to restart and how to request an actual telegram_gateway tg_status call. When no client connection was verified, the wizard prints the exact installed command to run again: `"/Library/Application Support/TelegramMCPGateway/bin/tg-mcp-owner" setup` (macOS), `"/opt/telegram-mcp-gateway/bin/tg-mcp-owner" setup` (Linux) or `C:\ProgramData\TelegramMCPGateway\bin\tg-mcp-owner.cmd setup` (Windows). SDK success is distinct from model tool loading. Defaults keep private chats/writes disabled. Repeat setup preserves sessions, grants and tokens; foreign/corrupt state or another release is not silently adopted.

Same-user software can observe human input/profile credentials, so agents and capture remain stopped during secret entry. Service isolation protects session/state from ordinary profiles; it is not a claim of protection from arbitrary software with the same user's privileges or approved sudo.
